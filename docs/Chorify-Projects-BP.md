# Chorify Projects：AI Native 团队协同开发系统 BP

## 一、项目概述

Chorify Projects 是面向 AI Native 团队的项目协同与交付管理系统。它服务的不是“无人负责的自动 Agent 团队”，而是真人负责人指挥 Codex 等 AI 工具完成工作，并将需求、任务、交付物、验收结论和操作记录统一沉淀到项目中。

系统希望解决 AI 辅助开发普及后的一个核心矛盾：执行速度显著提高，但工作上下文分散在不同会话、代码仓库和个人电脑中，责任、权限、成果与验收难以统一。

Chorify Projects 通过项目数据模型、个人 API Key 和标准操作协议，让真人团队与不同 AI 工具共享同一套可信项目上下文。

- 产品名称：Chorify Projects
- 产品形态：Web 项目协作平台 + API Key 项目操作接口
- 当前阶段：可运行的高保真、核心流程真实数据原型
- 在线环境：[https://aipms.sligenai.cn](https://aipms.sligenai.cn)
- 开源仓库：[SilentGenesisLab/chorify-projects](https://github.com/SilentGenesisLab/chorify-projects)

## 二、市场问题

### 1. AI 会话与项目事实脱节

团队成员在多个 Codex 会话中完成代码、文档和测试，但传统项目管理系统无法自动理解这些成果，任务长期停留在“待处理”，真实进展无法追踪。

### 2. AI 操作缺少真人身份与权限边界

直接把系统管理密钥交给 AI 风险过高；完全不开放接口，又使 AI 无法读取任务、对接人、依赖和验收标准。团队需要一种能将 AI 操作归属到真人，同时限制项目与动作范围的授权方式。

### 3. 任务完成与验收、发布混在一起

“代码写完”“任务提交”“验收通过”和“正式上线”是不同事实。缺少结构化流程时，团队容易把汇报当结果，把测试通过当发布成功。

### 4. 团队、项目与个人工作的权限耦合

成员需要自由创建和管理个人项目，也需要在团队框架下协同。团队身份不应限制个人工作空间，访客身份也不应影响成员在团队之外创建自己的项目。

### 5. 文档、文件和决策分散

需求依据、方案、交付物、Bug、版本和发布说明散落在聊天、网盘与本地目录，难以复用，也无法形成长期组织记忆。

## 三、产品方案

Chorify Projects 将协作拆成三个相互约束的层次：

1. **真人组织层**：团队、成员、职责、角色、OKR、贡献趋势和站内消息。
2. **项目交付层**：项目、需求、任务、Bug、版本、发布和文件引用。
3. **AI 授权层**：每位真人使用个人 API Key，让 Codex 在限定项目和权限内读取上下文、提交汇报及执行获准操作。

```text
真人提出目标与作出决策
          ↓
Chorify 统一项目事实、权限和验收标准
          ↓
Codex 在真人授权下读取上下文并完成执行
          ↓
工作汇报、交付物、验收与审计回到 Chorify
```

AI 不成为独立成员，不拥有业务责任，也不能自行作出正式验收或发布决定。

## 四、目标用户

| 用户 | 核心需求 |
| --- | --- |
| AI Native 创业团队 | 用少量成员协同多个 AI 会话，保证执行不失控 |
| 软件研发团队 | 管理需求、任务、Bug、版本、文件和发布闭环 |
| 产品与交付团队 | 统一客户需求、负责人、验收标准和交付证据 |
| 项目负责人 | 查看项目健康度、延期风险、版本进度和待验收事项 |
| 开发、算法和内容成员 | 获取自己的任务、依赖、对接人并提交结构化成果 |
| 管理者 | 查看团队职责、OKR、贡献趋势、操作记录和协同风险 |

## 五、核心业务闭环

### 1. 需求到交付

```text
需求草稿 → 评审中 → 已确认 → 开发中 → 已完成
                         ↓
             任务拆解、汇报与真人验收
```

需求可独立推进，也可以按需关联版本。临时需求不被强制纳入版本。

### 2. 任务提交与验收

```text
待处理 → 进行中 → 待验收 → 已通过 → 已完成
                       ↓
                    需修改
```

任务明确负责人、对接人、验收人、依赖、期限、交付物和验收标准。工作在其他 Codex 会话完成后，仍需提交结构化汇报并由真人验收。

### 3. Bug 到上线

```text
新建 → 已确认 → 已分配 → 修复中 → 待验证
→ 已验证 → 待发布 → 已关闭
```

Bug 分别记录发现版本和修复版本。修复验证通过不等同于已经上线。

### 4. 版本与发布

```text
规划中 → 开发中 → 测试中 → 待发布 → 已发布
```

版本聚合需求、任务和 Bug；发布记录保存构建标识、环境、负责人、结果和回滚说明，但不冒充真实部署系统。

## 六、当前功能

### 仪表盘

- 项目健康度和当前风险；
- 我的待办、逾期任务与待验收事项；
- 当前版本范围及完成进度；
- 最近项目活动。

### 团队管理

- 创建团队并自动成为所有者；
- 团队使命、介绍和职责范围；
- 成员岗位、个人介绍和团队职责；
- 所有者、管理员、成员、访客角色；
- 链接邀请、成员管理和角色调整；
- 团队 OKR、KR、对齐成员和进度检查；
- 今日、当月和近 30 日交付、协同与验收趋势；
- 指定成员消息、全员消息、收件箱和已读状态。

### 项目管理

- 所有登录用户均可创建个人项目；
- 正式团队成员可创建团队项目；
- 个人项目和团队项目独立筛选；
- 项目成员角色、职责和访问权限；
- 个人项目按账户名或手机号邀请注册用户；
- 个人项目可单向转入有权限的团队；
- 项目概览、里程碑、健康度和范围进度。

### 需求管理

- 需求增删改查；
- 背景、详细说明和验收条件；
- 优先级、发起人和参与人；
- 草稿、评审中、已确认、开发中、已完成状态；
- 目标版本可选；
- 关联任务、Bug 和文件。

### 任务中心

- “我的任务”和“我派出的任务”；
- 跨项目搜索和多条件筛选；
- 负责人、创建人、对接人和验收人；
- 优先级、期限、依赖、需求和版本关联；
- 结构化工作汇报；
- 真人验收通过或退回修改；
- 自动记录完成时间并进入贡献统计。

### Bug 管理

- Bug 增删改查；
- 严重程度、复现步骤和当前状态；
- 关联需求、任务、发现版本和修复版本；
- 从提出、修复、验证到待发布和关闭的完整流转。

### 版本与发布

- 版本目标、说明、负责人、参与人和计划日期；
- 聚合版本需求、任务和 Bug；
- 版本进度和里程碑；
- 发布构建、环境、清单、结果和回滚记录；
- 规划、开发、测试、待发布、发布、归档和取消状态。

### 文件管理

- 项目文件夹与文件元数据；
- 文件上传、版本历史和版本恢复；
- 文件标签、搜索和项目归属；
- 在需求、任务、Bug 和版本之间复用引用；
- 文件详情、分享和访问控制。

### 账户、权限与安全

- 手机号密码登录、手机号验证码和用户注册；
- 默认登录鉴权和未登录跳转；
- 账户名、密码、手机号和头像设置；
- 深色/浅色模式；
- 团队角色和项目角色解耦；
- API Key 多项目范围、细粒度权限、有效期和撤销；
- API Key 原文只显示一次，数据库只保存哈希；
- 网页操作和 API Key 操作统一进入审计日志。

## 七、差异化价值

### 1. 真人责任不被 AI 稀释

AI 的每次操作归属到授权用户；负责人、验收人和发布结论仍由真人承担。

### 2. 面向 Codex 的项目上下文协议

API Key 不只是开放接口密钥，还统一了项目范围、任务上下文、成员关系、依赖、交付物和验收标准，为不同 AI 工具提供一致的协作入口。

### 3. 个人项目与团队治理兼容

每位用户可独立创建项目和团队。团队访客权限只影响该团队内部资源，不影响个人项目及用户自己创建的新团队。

### 4. 将“完成”拆成可验证事实

系统区分执行、汇报、验收、发布和线上结果，使管理者能看到真实交付状态，而不只是一个被手动勾选的完成按钮。

### 5. 全链路可追溯

需求、任务、Bug、版本、文件和审计日志相互关联，既方便日常协作，也能沉淀交付 SOP 和组织知识。

## 八、商业化方向

### 目标客户

- 5–100 人的 AI Native 创业团队；
- 采用 Codex 等 AI 编程工具的软件团队；
- 需要强交付和验收留痕的技术服务团队；
- 管理多项目、多客户和多版本的产品研发组织。

### 产品分层设想

| 版本 | 核心能力 |
| --- | --- |
| 个人版 | 个人项目、任务、文件和个人 API Key |
| 团队版 | 团队项目、角色权限、OKR、消息和团队效能 |
| 企业版 | 单点登录、精细审计、合规策略、专属部署和服务支持 |

### 收费方式候选

- 按正式团队成员席位订阅；
- 按企业工作区或私有化部署收费；
- 高级审计、存储、集成和支持作为增值能力；
- API 调用本身不替代用户已有的模型或 Codex 费用。

收费方案仍需通过客户访谈、付费意愿和使用数据验证，不作为当前正式价格承诺。

## 九、阶段路线图

### 当前阶段：核心闭环可用

- 完善登录、团队、项目及权限体系；
- 打通需求、任务、验收、Bug、版本、发布和文件；
- 提供个人 API Key 和操作审计；
- 使用真实团队与真实项目持续验证。

### 下一阶段：形成稳定协作协议

- 补全项目、需求、任务、Bug、版本和文档 API；
- 发布可安装 CLI 与完整操作文档；
- 改善跨会话任务发现、成果回填和交付物关联；
- 增强通知、搜索、统计和异常处理；
- 建立接口兼容性和权限回归测试。

### 商业验证阶段

- 访谈 20 位目标客户并建立客户画像；
- 验证团队席位、私有化和增值功能的付费意愿；
- 选取 3–5 个真实团队进行持续试用；
- 衡量任务回填率、验收周期、版本延期和 AI 操作采用率。

## 十、关键指标

| 维度 | 建议指标 |
| --- | --- |
| 激活 | 创建首个项目、首项需求和首个 API Key 的用户比例 |
| 使用 | 周活跃团队、活跃项目、有效任务和 API 操作次数 |
| 协作 | 有负责人/验收人的任务比例、工作汇报提交率、跨会话成果回填率 |
| 交付 | 按期完成率、验收周期、返工率、版本发布成功率 |
| 留存 | 团队 4 周与 12 周留存、项目持续活跃率 |
| 商业 | 试用转付费率、每团队席位数、企业版线索与续费率 |
| 安全 | 越权请求拦截、过期/撤销 Key 命中和高风险操作审计覆盖率 |

任务数量不直接等同于个人绩效，指标用于发现协作和系统问题。

## 十一、技术与部署

- Next.js App Router、React、TypeScript；
- Tailwind CSS 与 Lucide 图标；
- PostgreSQL 与 Prisma 6；
- 手机号密码和阿里云短信验证码；
- S3 兼容文件存储能力；
- Docker Compose 预发布部署；
- Nginx 反向代理和健康检查；
- GitHub `main` / `uat` 分支协作与服务器拉取部署。

## 十二、主要风险与应对

| 风险 | 应对方向 |
| --- | --- |
| AI 工具或模型接口快速变化 | 保持项目协议与具体模型解耦，使用稳定 REST/CLI 接口 |
| API Key 泄露 | 一次性展示、哈希存储、项目和权限最小化、有效期、撤销与审计 |
| 团队不愿额外维护任务 | 从 Codex 会话直接提交汇报，减少重复录入 |
| 数据变成形式主义 | 强制交付物和验证证据，不把任务数量直接用于绩效 |
| 产品范围过宽 | 围绕“真人指挥 AI、成果可验收”核心闭环优先建设 |
| 企业采购周期较长 | 先通过小团队版验证使用频率和留存，再扩展企业能力 |

## 十三、当前结论

Chorify Projects 的机会不是再做一个传统项目管理看板，而是为 AI 已经参与日常执行的团队建立新的协作底座：真人掌握目标、权限和结论，AI 获得结构化上下文并加速执行，所有成果重新回到可追踪、可验收、可发布的项目闭环中。

项目当前已经具备端到端原型和真实团队验证条件，下一步重点是补齐开放接口与 CLI、提高稳定性，并用目标客户访谈验证高频场景、部署偏好和付费路径。
